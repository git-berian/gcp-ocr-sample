# テスト作成ガイドライン

## 目的

テストカバレッジを上げることではなく、仕様と振る舞いを保証する。

## 進め方

### ステップ 1: 仕様分析（コードは書かない）

テスト対象のコードを読み、以下を整理する：

- **テストの粒度**: 単体 / 統合 / E2E のどれが適切か
- **このコードの責務**
- **外部から見た振る舞い**
  - 正常系
  - 境界値
  - 異常系
  - 条件分岐
- **外部依存とモック方針**: 何をモックし、何をモックしないか
- **テストしないこと**: スコープ外を明示する
- **仕様が曖昧な点**: 勝手に決めず、仮定として明示する

### ステップ 2: テストコードを書く

- 既存テストのスタイル・命名規則・ヘルパー関数を踏襲する
- 各テストケース名は「何を保証しているか」が分かる名前にする
- リファクタで壊れないテストにする（内部実装ではなく振る舞いを検証する）
- モックはステップ 1 で決めた方針に従う

### ステップ 3: 未カバー観点の報告

テストで未カバーの観点や追加で検討すべき点を優先度付きで示す。

## 避けること

- カバレッジ目的の表面的なテスト
- 関数を呼ぶだけで期待値検証が弱いテスト
- 内部実装に密結合なテスト
- 正常系だけのテスト
- 過剰なモック
