# コードレビューガイドライン

## 目的

lint/format/型チェック等ツールが捕捉できない設計・振る舞い・安全性の問題を見つける。
スタイル指摘や好みの押し付けではなく、バグ・リスク・保守性に焦点を当てる。

## 進め方

### ステップ 1: 変更の全体像を把握する（コードの詳細に入らない）

- 変更の目的と背景（Issue / PR 本文）を確認する
- 変更対象のファイル一覧・差分の規模を把握する
- 「この変更は1つの目的に絞られているか」を判断する

### ステップ 2: レビュー観点に沿って差分を確認する

以下の観点を優先度順に確認する：

1. **正しさ**: 仕様どおりに動くか。エッジケースで壊れないか
2. **安全性**: 入力バリデーション、認証・認可、シークレット露出
3. **エラーハンドリング**: 外部呼び出し・I/O の失敗パスが処理されているか
4. **設計**: レイヤー違反がないか、既存パターンとの一貫性
5. **テスト**: 変更に対応するテストがあるか、テストが振る舞いを保証しているか
6. **保守性**: 将来の変更者が理解しやすいか、不要な複雑さがないか

### ステップ 3: 指摘を重要度付きで報告する

- **must**: マージをブロックする問題（バグ、セキュリティ、データ損失リスク）
- **should**: 強く推奨する改善（設計上の問題、テスト不足）
- **nit**: 任意の改善提案（命名、可読性の微調整）

各指摘に「何が問題か」「なぜ問題か」「どう直すか」を含める。

## 避けること

- ツールが検出できること（lint, format, 型エラー）への指摘
- 個人の好みレベルのスタイル指摘
- 変更範囲外のコードへの指摘（別 Issue で対応すべき）
- 具体的な改善案のない「なんとなく気になる」指摘
- 変更の目的と無関係なリファクタリング要求
