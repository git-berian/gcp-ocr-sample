# ADR-0009: DDD の採用範囲

## ステータス

承認

## コンテキスト

ADR-0001 でクリーンアーキテクチャ（domain / application / infrastructure の層分け）を採用したが、DDD の戦術的設計（エンティティ・値オブジェクト・集約・リポジトリ・ドメインサービス）をどこまで採用するかは未定義のままだった。

その結果、以下のような曖昧さが残っていた：

- `domain/mime-type.ts` は単なる関数で、値オブジェクトの形を取っていない
- `application/parse-document.ts` の `DocumentEntity` 型は Document AI の抽出結果フィールドを表すが、DDD の Entity と命名衝突する
- 新しいドメインルールを追加するとき、どこにどう書くべきかの指針がない

判断軸を明文化しないと、過剰設計（小さなアプリにフル DDD を入れる）と過小設計（ドメインルールが domain 層の外に漏れる）の両方が起きる懸念がある。

## 決定

DDD の戦術的設計は、現段階では以下の範囲で採用する。

- **値オブジェクト (Value Object)**: 採用する
  - 「値そのものに制約・ルールがあるもの」は値オブジェクト化する
  - 不正な値を持つインスタンスを構築不可能にする設計（private constructor + static ファクトリ）を取る
- **エンティティ (Entity)**: 採用しない（当面）
  - 永続化や状態遷移が必要になった時点で導入する
- **集約 (Aggregate)**: 採用しない（当面）
  - 複数のエンティティの整合性境界が必要になった時点で導入する
- **リポジトリ (Repository)**: 採用しない（当面）
  - 永続化が必要になった時点で導入する
  - 現状の `DocumentProcessor` インターフェースはリポジトリではなく、外部サービスゲートウェイ (Gateway / Anti-Corruption Layer) として位置づける
- **ドメインサービス (Domain Service)**: 採用しない（当面）
  - 複数の値オブジェクト/エンティティを跨ぐロジックが出た時点で導入する

将来の導入トリガー：

| 戦術的設計       | 導入トリガー                                                                                    |
| ---------------- | ----------------------------------------------------------------------------------------------- |
| エンティティ     | 同じ概念に ID と複数の状態が出てきたとき（例: `Document` が draft / confirmed / archived など） |
| 集約             | 複数のエンティティをまとめて整合性を保ちたいとき                                                |
| リポジトリ       | Firestore など永続化層を導入するとき                                                            |
| ドメインサービス | どの値オブジェクト/エンティティにも属さない、跨ぎロジックが必要になったとき                     |

## 理由

- **現状のドメインがシンプル**: OCR を 1 回呼ぶだけ、永続化なし、状態遷移なし。戦術的 DDD をフルに入れてもメリットが出ない
- **値オブジェクトだけは費用対効果が高い**: 「不正な MIME タイプを持つインスタンスは存在しない」のように、ドメインルールを型で表現できるため、コストに対するリターンが大きい
- **導入トリガーを先に決める**: 「永続化が必要になったらリポジトリを入れる」のように、判断基準を ADR に残すことで、将来の判断ブレを防ぐ
- **過剰設計と過小設計の両方を避ける**: 何を入れるか・何を入れないかを両方明示する

代替案として「フル DDD を最初から導入」「層分けのみで DDD 用語を一切使わない」も検討したが、前者は YAGNI 違反、後者は将来ドメインが育ったときの導入判断が遅れるリスクがある。

## 影響

- `domain/` 配下の値オブジェクトは「不正な値を持つインスタンスを構築不可能にする」設計を取る（private constructor + `static from()` ファクトリで不正値は例外を投げる）
- 値オブジェクトの `static from()` が投げる例外（ドメイン例外）は、**境界層（handlers / 入力 adapter）で必ず捕捉し、HTTP では 4xx（入力不正）に正規化する**
  - Firebase Functions Callable では `HttpsError("invalid-argument", ...)` に変換する
  - 既存の `infrastructure/request-validator.ts` のように **エラーを値（`ValidationError`）で返すスタイルとも互換性がある**（境界で `try/catch` してエラー値に変換する）
  - ドメイン例外が境界を越えて 5xx として漏れるのは禁止する
- 入力検証のうち**ドメインルールに該当するもの**（許可リストなど）は、`infrastructure/` の validator ではなく `domain/` の値オブジェクトに寄せる
- 将来エンティティを導入する場合、Document AI 由来のレスポンス型（現 `DocumentEntity` 型）と命名衝突しないよう、別 PR で `ExtractedField` 等にリネームする
- 戦術的設計の導入は段階的に行い、各導入時に別 ADR を立てて意思決定を残す

### 補足: infrastructure 層のサブディレクトリ分割方針（将来）

infrastructure 層のファイル構成についても、当面の方針を以下に記す。実装は今回行わず、必要になった時点で別 ADR を立てて分割する。

- **当面はフラットな構成で運用する**（現状 4 ファイル）
- **5 ファイル超、または同系統が 3 つ以上揃った時点で「対象システム別」のサブディレクトリに切る**
  - 例: `infrastructure/{http,auth,document-ai,firestore}/`
- 分割の単位は **対象システム別** とする
  - 理由: ADR-0001 の動機（外部サービスの影響範囲を絞る）と整合し、サービス丸ごとの差し替え単位とディレクトリが一致する
  - technical concern 別（`validators/`, `clients/`, `repositories/`）は採用しない（1 つの外部サービスに関するファイルが分散するため）
